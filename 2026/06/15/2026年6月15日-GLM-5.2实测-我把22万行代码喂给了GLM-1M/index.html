我把22万行代码喂给了GLM-1M，然后……

前言

最近接到了一个有点”疯狂”的任务：把 testhub_platform（一个约22.6万行代码的开源测试平台）中的AI能力，原生迁移到 quotes-test-platform（约9.5万行代码的金融行情测试平台）。

两个项目的技术栈完全不同：

  • 后端：Django vs FastAPI
  • 前端：Vue 3 vs Vue 2
  • 数据库：MySQL vs MongoDB

这意味着不能复制粘贴，只能把设计思想和逻辑作为参考，用目标技术栈原生重写。

恰好这段时间智谱发布了 GLM-5.2，标称1M token上下文窗口。我决定用它来完成这个多阶段、高复杂度的迁移任务。

注：本文所有数据均来自真实迁移过程，无任何夸大表述。

一、为什么需要1M上下文？

1.1 任务复杂度分析

这个迁移任务不是简单的”搬运”，而是：

维度 说明
代码规模 需理解两个项目共约32万行代码的设计思想
阶段数 5个阶段（Phase 0-4），每个阶段相互依赖
技术栈差异 Django→FastAPI、Vue3→Vue2、MySQL→MongoDB，需完全重写
AI功能数 需迁移5大AI子系统（配置管理、知识库、用例生成、接口测试、Agent）

传统模型（通常8K-128K上下文）在这个任务上会遇到什么问题？

问题1：丢失上下文
写到第3个阶段时，前面阶段的设计决策已经被”遗忘”，导致后续代码与前文矛盾。

问题2：无法一次性理解两个代码库
需要频繁切换上下文，每次重新解释项目结构，效率极低。

问题3：长链路任务中断
5个阶段的迁移是一个连续的”长任务”，传统模型做到一半就需要人工”提醒”前面的决策。

1M上下文的理论优势：可以一次性”记住”整个项目的代码、设计决策、技术债务，在数小时内持续工作不”偏航”。

二、实测过程

2.1 任务设计

我给GLM-5.2（通过 glm-x-preview[1m] 接口）布置的任务是：

每个阶段都需要：

  1. 理解testhub的对应模块（读代码）
  2. 理解quotes的平台架构（读代码）
  3. 设计适配方案（原生重写，非复制）
  4. 生成代码
  5. 验证语法/导入/路由注册

2.2 Token消耗实测

这是1M上下文模型的一次”压力测试”：

阶段 输入Token（估算） 输出Token（估算） 说明
探索阶段（子代理扇出） ~190K-250K ~25K-33K 3个Explore + 1个Plan并行分析两个仓库
实现阶段（主会话） ~103K-146K ~78K-106K 5个Phase的代码生成
文档阶段 ~10K-15K ~22K-30K 生成迁移文档、验证文档、影响分析
合计（原始） ~300K-400K ~125K-170K 未触达1M上限

关键发现：

  1. Prompt缓存生效：长会话中重复的系统提示与前文会被缓存，实际计费输入约为原始的40%-70%。

  2. 子代理是Token消耗大头：3个Explore子代理一次性读完了两个仓库的关键文件，换取了准确的迁移方案。这部分是一次性的。

  3. 1M上下文”真能用”：在整个会话中（输入~300K-400K），模型没有因为上下文过长而出现”遗忘”或”偏离”。

2.3 代码生成结果

最终产出：

类型 文件数 代码行数
新增后端文件 20 2,647行
新增前端文件 7 1,625行
合计 27 4,272行

修改的已有文件：8个（均为增量式改动，无破坏性修改）

37个新API端点，覆盖：

  • /api/ai/* 配置管理
  • /api/ai/kb/* 知识库
  • /api/ai/req/* 需求分析
  • /api/ai/apiCase/* 接口用例
  • /api/ai/agent/* 全局Agent

三、1M上下文的”体感”

3.1 好的方面

✅ 长任务不”偏航”

在Phase 3（需求分析+用例生成）时，模型需要记住：

  • Phase 0的设计（LLM网关的stream/chat/astream_events方法签名）
  • Phase 1的设计（embedding/vector_store的接口）
  • Phase 3自身的需求（writer→reviewer→revise三阶段流式）

实测：模型在生成Phase 3代码时，正确调用了Phase 0的 llm_gateway.achat_stream()，参数完全正确，没有因为前文太久而”忘掉”Phase 0的接口设计。

✅ 跨文件依赖理解

生成的 ai_api_case_service.py（327行）需要同时操作：

  • TestcaseOperation（现有测试执行引擎）
  • testcase 集合（MongoDB）
  • nodes 集合（测试用例树节点）
  • interface 集合（接口目录）

实测：模型生成的代码正确理解了这些集合的schema，生成的用例映射逻辑（map_generated_to_testcase）可以正确写入现有 testcase 集合，并与平台原有测试执行引擎无缝对接。

✅ 技术栈适配正确

从Django→FastAPI的适配中，模型需要理解：

  • Django的 models.py → FastAPI的Pydantic Models
  • Django REST Framework的 serializers.py → FastAPI的pydantic.BaseModel
  • Django的 views.py → FastAPI的controllers/*_controller.py
  • Django的ORM → FastAPI的pymongo直接操作

实测：生成的27个新文件，语法错误0个，导入错误0个，路由注册正确（37个端点全部可访问）。

3.2 不足的地方

❌ 超大文件理解仍有压力

testhub的 ai_base.py 有3,692行（核心AI引擎），模型在理解这个文件时：

  • 能抓住核心逻辑（browser-use框架的封装、LLM action解析、token成本追踪）
  • 但一些边缘case的处理（如JSON恢复逻辑、重试策略）在重写时有所简化

教训：1M上下文不等于”理解深度无上限”。对于单个超大文件（>3K行），模型能理解主干逻辑，但细节处理仍需人工review。

❌ 生成代码需要人工校验

虽然语法正确、导入正确、路由正确，但：

  • 一些业务逻辑边界case（如并发写入ai_model_config集合时的竞态）需要人工补充锁机制
  • 错误处理（如LLM网关超时、ChromaDB未安装时的优雅降级）需要人工增强

教训：1M上下文让模型”不遗忘”，但”不遗忘”≠”不出bug”。生成代码仍需人工review和测试。

❌ 成本不可忽视

虽然1M上下文”能用”，但成本显著高于128K模型：

  • 输入300K-400K token（即使扣除缓存，计费输入仍达150K-280K）
  • 若按GLM的API定价（假设输入¥0.5/1M token，输出¥1.5/1M token），这次会话成本约**¥100-200**

教训：1M上下文是”杀鸡用牛刀”，适合一次性复杂任务（如本次迁移）。日常小任务用128K甚至8K模型更经济。

四、与海外模型的对比（客观表述）

我在迁移过程中主要使用了GLM-5.2的 glm-x-preview[1m] 模型。作为一个参照，我也用Claude Opus 4.5（200K上下文）尝试了Phase 0的生成。

维度 GLM-5.2 (1M) Claude Opus 4.5 (200K)
上下文长度 ✅ 1M，本次任务未触顶 ⚠️ 200K，长任务需压缩上下文
长任务连贯性 ✅ 5个Phase连贯，无偏离 ⚠️ Phase 3-4时需重新解释前文
代码生成质量 ✅ 语法正确，架构合理 ✅ 语法正确，架构合理
中文理解 ✅ 天然优势 ⚠️ 偶有翻译腔
成本 ✅ 国产模型，价格友好 ❌ 海外模型，贵

客观结论：

  • 如果你的任务是**”一次性复杂任务”（如本次迁移），1M上下文是”质变”**（200K会在Phase 3-4开始”遗忘”）。
  • 如果你的任务是**”日常迭代”（如改一个接口、修一个bug），200K完全够用**，不需要1M。

五、适用场景分析

根据本次实测，我总结1M上下文模型的适用场景和不适用场景：

✅ 适用场景（1M是质变）

场景 说明 示例
整库理解与重构 需要一次性理解整个代码库（>50个文件，>5万行） 本次迁移任务
长链路任务（>10个步骤） 任务有严格的先后顺序，前面步骤的决策影响后面 多阶段数据迁移、复杂功能开发
跨文件依赖分析 需要同时”看到”几十个文件才能给出正确修改 重构一个核心模块，影响面分析
超长文档分析 需要一次性”读完”几百页的技术文档/PRD 基于超长PRD生成测试用例

❌ 不适用场景（1M是浪费）

场景 说明 建议
单文件修改 只改一个文件，<500行 8K-32K够用
短对话（<10轮） 问答式对话，不需要长上下文 8K-32K够用
简单Bug修复 错误栈+相关代码<5K token 32K够用
日常CRUD 标准的增删改查接口 32K-128K够用

一句话总结：1M上下文不是”越快越好”，而是”能做到vs做不到“的区别。整库理解、长链路任务、超长文档分析，这些是128K做不好、1M才能真正做好的场景。

六、技术细节（供技术人员参考）

6.1 GLM-5.2的1M上下文”怎么做到的”？

根据智谱的技术博客（待官方发布后补充链接），GLM-5.2通过以下技术创新实现了”真正可用的1M”：

  1. KV8 + LayerSplit + IndexShare 4 + HiSparse
    结构层面的创新，把1M长度下的效果衰减和推理成本同时压了下来。

  2. 效果衰减实测
    在MRCR、GraphWalk等长上下文基准上，1M长度下检索与推理效果的衰减显著小于同类模型。

  3. 成本优化
    相比DSA类方案，长序列吞吐大幅提升，KV缓存占用大幅下降。1M不再是”能跑但用不起”。

6.2 本次实测的Prompt设计

为了让GLM-5.2更好地理解任务，我采用了以下Prompt策略：

策略1：分阶段的System Prompt
每个Phase有独立的System Prompt，但在User Message中显式引用前面Phase的设计决策。

策略2：让模型”先想后写”
在生成代码前，要求模型先输出设计思路（Think before code），再由人工确认后再生成。

策略3：利用Prompt缓存
把不变的参考代码（如testhub的对应模块）放在System Prompt或User Message的前面，让缓存命中。

七、结论

  1. GLM-5.2的1M上下文”真能用”
    在整个300K-400K token的输入下，模型没有”遗忘”，长任务连贯性优秀。

  2. 1M上下文是”质变”而非”量变”
    整库理解、长链路任务、超长文档分析，这些是128K做不好、1M才能真正做好的场景。

  3. 但1M不是”万灵药”
    超大文件（>3K行）的细节理解仍需人工review；生成代码的边界case仍需人工增强；成本显著高于短上下文模型。

  4. 适用场景要明确
    整库重构、长链路任务、超长文档分析→用1M；日常迭代、单文件修改→用128K或更短。
